efsa-additives-rag

Asistente RAG sobre dictámenes regulatorios de reevaluación de aditivos alimentarios (EFSA, Reglamento UE 257/2010)
LangGraph RAG MCP Ciencia de alimentos Portfolio

objetivo

Demostrar diferenciación técnica real combinando ingeniería de IA (LangGraph, RAG, MCP) con dominio profundo en química / ciencia de alimentos (6 años de investigación, patente en extracción de bioactivos, 30+ publicaciones). No es un ejercicio de "aprender un framework" — es un sistema que solo alguien que sabe leer un dictamen EFSA de verdad puede diseñar bien, en particular la lógica de verificación de vigencia (nodo 3).

por qué este proyecto y no otro

Un proyecto anterior (skillgap-agent) se descartó como pieza insignia por ser una idea de portfolio genérica y saturada. Este proyecto existe específicamente para no repetir ese error: la razón de ser es la diferenciación de dominio, no la ejecución técnica en sí, que reutiliza patrones ya dominados.

audienciaqué busca ver
reclutador / entrevistador técnico Evidencia de criterio de ingeniería real: decisiones justificadas con datos, no solo "usé LangGraph". Que el candidato sepa cuándo NO usar un LLM (lookups estructurados) y cuándo sí (síntesis narrativa).
persona con interés en seguridad alimentaria Explorar el historial de reevaluación de un aditivo con citas verificables al EFSA Journal exacto — sin que el sistema jamás actúe como asesoría regulatoria.
límite de propósito — no negociable

Esta es una herramienta de exploración de literatura regulatoria, no de asesoramiento regulatorio. Debe quedar explícito en la UI y en el README. El sistema nunca debe afirmar si un aditivo "es seguro" — solo debe citar lo que dice el dictamen correspondiente.

cómo funciona

Dos fuentes de datos → orquestador LangGraph de 4 nodos → dos superficies de exposición

capa de datos — dos fuentes, roles distintos

OpenFoodTox (xlsx, ~7.880 sustancias)
Fuente de verdad para todo lo cuantificable: ADI/TDI/NOAEL, fechas de dictámenes, DOIs. Consulta determinista, cero riesgo de alucinación.
+
PDFs de dictámenes de reevaluación (~162 documentos únicos)
Fuente para lo cualitativo: discusión de incertidumbre, razonamiento del panel, por qué cambió un valor entre reevaluaciones.

orquestador LangGraph — el diferenciador real

1. Extracción de entidad
LLM identifica qué aditivo / E-number pregunta el usuario.
↓
2. Retrieval híbrido
Query estructurada contra OpenFoodTox (valores) + búsqueda vectorial contra Chroma (contexto narrativo).
↓
3. Verificación de vigencia
Cadena de joins determinista: FLEX_SUM.ToxRefValues → DOSSIER_DOCS → DOSSIER, ordenado por fecha, filtrado por tipo "EFSA opinion". LLM solo si el resultado es ambiguo.
↓
4. Generación con cita obligatoria
Redacta la respuesta citando el número exacto de EFSA Journal / DOI recuperado. Nunca "según un documento".

exposición — dos superficies, mismo grafo

superficierol
servidor MCPsearch_efsa_opinion(substance), get_reevaluation_status(substance) — wrapper del razonamiento, no de la base de datos (a diferencia de mcp-openfoodtox, ya existente y desactualizado desde 2023).
UI Streamlit / GradioDemo interactiva, sin lógica propia. Incluye botón de refresco de corpus con candado server-side de 24h.
verificado con datos reales, no supuesto

La cadena de joins del nodo 3 se probó con aspartamo (E 951): 5 registros de ADI enlazan a dictámenes de 2006, 2009 (×2), 2011 y 2013 — MAX(fecha) filtrado por tipo devuelve correctamente la reevaluación de 2013.

nodo 4 — especificación de comunicación de riesgo

El ADI/NOAEL ya documenta consecuencias para la salud (efecto crítico, órgano afectado, estudio pivotal) vía CriticalEndpoint, TargetSystemOrganToxicity y la sección Discussion de END_SUM — no hace falta ninguna fuente externa para esto. Lo que sí exige cuidado es cómo se redacta.

// system prompt — restricción obligatoria del nodo 4 SIEMPRE aclarar: el ADI incluye un factor de incertidumbre (normalmente ×100 sobre el NOAEL) — el valor ya está muy por debajo de la dosis a la que se observó el efecto crítico. PROHIBIDO redactar: "si se supera el ADI, se produce/puede producir [efecto]" — el ADI es un límite de exposición segura con margen incorporado, no un umbral de toxicidad. FÓRMULA CORRECTA: "el ADI incorpora un margen de seguridad de [factor] veces por debajo de la dosis a la que se observó [efecto] en el estudio pivotal [especie/duración]".
por qué esto no es opcional

Confundir "límite de exposición con margen de seguridad" con "umbral de toxicidad" es un error científico, no solo de tono — y en un sistema de seguridad alimentaria, redactarlo mal equivale a generar alarmismo con datos reales. Esta restricción va en el system prompt, no se deja a criterio del LLM.

herramientas

Qué hace cada pieza del stack y por qué se eligió
// ingesta y datos estructurados pandas / openpyxl — lectura y joins sobre OpenFoodTox (xlsx) requests — descarga de PDFs desde EFSA / Zenodo // RAG LangChain — PyPDFLoader, RecursiveCharacterTextSplitter sentence-transformers — embeddings locales (coste cero) Chroma — vector store, local // orquestación LangGraph — grafo de 4 nodos (ver ARCHITECTURE.md) DeepSeek V4-Flash — LLM de razonamiento ($0.14/$0.28 por 1M tokens) // exposición MCP — servidor de herramientas reutilizables Streamlit — UI de demo // hosting HF Spaces / Streamlit Community Cloud — tier gratuito

por qué DeepSeek y no un modelo local para producción

Con ~3.000 tokens de entrada y ~500 de salida por consulta, el coste ronda $0.0006 por consulta. Un presupuesto de 6-7€/mes cubre 10.000-12.000 consultas — muy por encima de lo que un portfolio necesita. El caché automático de DeepSeek (prompt de sistema repetido) baja esto aún más.

por qué embeddings locales y no vía API

El botón de refresco reindexa contenido nuevo cada vez que se pulsa (dentro del límite de 24h). Si los embeddings fueran de pago, cada refresco tendría coste variable no acotado por el candado del botón. Con sentence-transformers local, el refresco solo consume cómputo del hosting, no dinero.

paso a paso de construcción

Orden de implementación, no de arquitectura
1
QA final del corpus pendiente

Cruzar los 162 dictámenes filtrados (Domain.FoodDomain == 'food additives' + "re-evaluation" u otros patrones de título equivalentes ("extension of use", "statement on", "reconsideration of the ADI", "safety assessment... as a food additive") en título, más el rescate de dictámenes reales mal etiquetados con otro dominio) contra las calls for data activas conocidas (ribonucleótidos E626-635, ácido glucónico E574-579, aditivos en forma gaseosa) para detectar huecos.

2
Descarga manual asistida por checklist en curso

No es un script de descarga automatizado: las 3 fuentes probadas (Wiley directo vía DOI, efsa.europa.eu, PubMed Central) bloquean peticiones automatizadas -- Wiley con un challenge de Cloudflare sin excepción, efsa.europa.eu porque solo redirige a la misma Wiley, y PMC con falsos positivos de búsqueda por DOI, necesidad de curl en vez de requests, y captcha intermitente incluso así. El bloqueo es específico de peticiones automatizadas -- un navegador con sesión humana normal no debería toparse con el mismo challenge, así que la descarga es manual. Checklist generado (scripts/generate_pdf_checklist.py → data/pdf_download_checklist.csv / .md) con sustancia, E-number, DOI, título, nombre de archivo esperado y columna para marcar progreso -- 161 dictámenes únicos (el corpus de 162 tiene un duplicado real por una errata de título en el xlsx, ver CLAUDE.md).

3
Script de ingesta OpenFoodTox

Implementar en pandas la cadena de joins verificada: FLEX_SUM.ToxRefValues → DOSSIER_DOCS → DOSSIER. Tests contra el caso aspartamo como referencia.

4
Chunking + embeddings + Chroma

Trocear los PDFs, generar embeddings locales, poblar el vector store. Definir estrategia de chunk size/overlap sobre el contenido real (no genérica).

5
Nodos del grafo LangGraph

Implementar los 4 nodos con tests unitarios por nodo, en particular el heurístico + fallback del nodo 3.

6
Servidor MCP

search_efsa_opinion y get_reevaluation_status como wrapper del grafo compilado.

7
UI Streamlit

Interfaz de consulta + botón de refresco con candado server-side de 24h (archivo de bloqueo, o almacenamiento externo si el hosting es efímero).

8
Deploy + README

HF Spaces o Streamlit Community Cloud. README con las limitaciones documentadas explícitamente (ver LIMITATIONS.md), no ocultas.

9
Refresco incremental automatizado futuro, no MVP

GitHub Action programada que compare versión de OpenFoodTox y solo procese lo nuevo. Fuera de scope del portfolio inicial — documentado como mejora futura, no como deuda oculta.

limitaciones conocidas

Lo que hay que documentar en el README con honestidad, no maquillar
cobertura del corpus no verificada al 100%

Los 162 dictámenes se obtuvieron filtrando por dominio + patrón de texto en el título ("re-evaluation" u otros patrones equivalentes verificados uno por uno contra falsos positivos: "extension of use", "statement on", "reconsideration of the ADI", "safety assessment... as a food additive"), con un rescate adicional para dictámenes reales mal etiquetados con otro dominio (18 casos: acesulfamo K, sacarina, plata E174 entre otros) — no por un campo estructural fiable. No existe una tabla pública única de EFSA para validar 1:1. Riesgo de falsos negativos si algún dictamen usa otra terminología en el título.

nodo 3 es heurístico, no infalible

MAX(fecha) filtrado por Type == 'EFSA opinion' funciona en los casos probados, pero no hay garantía general si existen dos opiniones del mismo tipo muy próximas en el tiempo sin que el título aclare cuál sustituye a cuál.

actualización no es en tiempo real, por diseño

OpenFoodTox se publica por versiones (no como feed en vivo), y el programa de reevaluación sigue activo en 2026. El botón de refresco es una comprobación bajo demanda con candado de 24h, no un sistema de vigilancia continua — decisión de diseño explícita, no limitación técnica no resuelta.

candado por archivo depende del hosting

Si el despliegue usa almacenamiento efímero (contenedores que se reinician), el archivo de bloqueo del botón puede perderse antes de las 24h. Si esto importa, mover el candado a almacenamiento externo persistente.

coste de operación — resuelto

Embeddings locales + DeepSeek V4-Flash con caché automático: coste estimado muy por debajo de 6-7€/mes incluso con miles de consultas. No es una barrera del proyecto.
